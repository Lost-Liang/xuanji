# 规划与任务拆分

## 概述

将工作分解为有明确验收标准的小型、可验证任务。良好的任务拆分是 agent 能可靠完成工作与产生一团混乱的区别。每个任务应该小到可以在单个专注会话中实现、测试和验证。

## 何时使用

- 有规格需要拆分为可实现的单元
- 任务感觉太大或太模糊无法开始
- 工作需要跨多个 agent 或会话并行化
- 需要向人类沟通范围
- 实现顺序不明显

**何时不使用：** 范围明显的单文件变更，或规格已包含明确定义的任务。

## 规划流程

### 步骤 1：进入计划模式

编写任何代码之前，以只读模式操作：

- 阅读规格和相关代码库部分
- 识别现有模式和约定
- 映射组件间依赖关系
- 记录风险和未知项

**规划期间不要编写代码。** 输出是保存到 `tasks/plan.md` 的计划文档和保存到 `tasks/todo.md` 的任务列表，不是实现。

### 步骤 2：识别依赖图

映射什么依赖什么：

```
数据库模式
    │
    ├── API 模型/类型
    │       │
    │       ├── API 端点
    │       │       │
    │       │       └── 前端 API 客户端
    │       │               │
    │       │               └── UI 组件
    │       │
    │       └── 验证逻辑
    │
    └── 种子数据 / 迁移
```

实现顺序遵循依赖图自底向上：先构建基础。

### 步骤 3：垂直切片

不是先构建所有数据库，再所有 API，再所有 UI——一次构建一条完整功能路径：

**坏的（水平切片）：**

```
任务 1：构建整个数据库模式
任务 2：构建所有 API 端点
任务 3：构建所有 UI 组件
任务 4：连接所有东西
```

**好的（垂直切片）：**

```
任务 1：用户可以创建账户（注册的模式 + API + UI）
任务 2：用户可以登录（认证的模式 + API + UI）
任务 3：用户可以创建任务（任务的模式 + API + UI）
任务 4：用户可以查看任务列表（查询 + API + UI）
```

每个垂直切片交付可工作、可测试的功能。

### 步骤 4：编写任务

每个任务遵循此结构：

```markdown
## 任务 [N]：[简短描述性标题]

**描述：** 一段说明此任务完成什么。

**验收标准：**
- [ ] [具体、可测试的条件]
- [ ] [具体、可测试的条件]

**验证：**
- [ ] 测试通过：[仓库的聚焦测试命令]
- [ ] 构建成功：[仓库的构建命令]
- [ ] 手动检查：[要验证什么]

**依赖：** [依赖的任务编号，或"无"]

**可能涉及的文件：**
- `src/path/to/file.ts`
- `tests/path/to/test.ts`

**估算范围：** [小：1-2 个文件 | 中：3-5 个文件 | 大：5+ 个文件]
```

### 步骤 5：排序和检查点

排列任务使得：

1. 依赖被满足（先构建基础）
2. 每个任务让系统处于可工作状态
3. 每 2-3 个任务后有验证检查点
4. 高风险任务靠前（快速失败）

添加显式检查点：

```markdown
## 检查点：任务 1-3 后
- [ ] 所有测试通过
- [ ] 应用构建无错误
- [ ] 核心用户流程端到端工作
- [ ] 继续前与人类一起审查
```

## 任务大小指南

| 大小 | 文件 | 范围 | 示例 |
|------|-------|-------|---------|
| **XS** | 1 | 单个函数或配置变更 | 添加验证规则 |
| **S** | 1-2 | 一个组件或端点 | 添加新 API 端点 |
| **M** | 3-5 | 一个功能切片 | 用户注册流程 |
| **L** | 5-8 | 多组件功能 | 带筛选和分页的搜索 |
| **XL** | 8+ | **太大 —— 进一步拆分** | — |

如果任务是 L 或更大，应该拆分为更小的任务。Agent 在 S 和 M 任务上表现最佳。

**何时进一步拆分任务：**

- 会超过一个专注会话（约 2+ 小时的 agent 工作）
- 无法用 3 个或更少的要点描述验收标准
- 涉及两个或更多独立子系统（如认证和计费）
- 发现自己在任务标题中写"和"（表明这是两个任务）

## 输出文件

- **计划文档：** 将实现计划保存到 `tasks/plan.md`。
- **任务列表：** 将检查清单式任务列表保存到 `tasks/todo.md`。

如果 `tasks/` 目录不存在则创建。这些路径是 `/build` 命令和其他下游工具期望的约定。

## 计划文档模板

```markdown
# 实现计划：[功能/项目名称]

## 概述
[我们在构建什么的摘要]

## 架构决策
- [关键决策 1 及理由]
- [关键决策 2 及理由]

## 任务列表

### 阶段一：基础
- [ ] 任务 1: ...
- [ ] 任务 2: ...

### 检查点：基础
- [ ] 测试通过，构建干净

### 阶段二：核心功能
- [ ] 任务 3: ...
- [ ] 任务 4: ...

### 检查点：核心功能
- [ ] 端到端流程工作

### 阶段三：收尾
- [ ] 任务 5: ...
- [ ] 任务 6: ...

### 检查点：完成
- [ ] 所有验收标准满足
- [ ] 准备审查

## 风险与缓解
| 风险 | 影响 | 缓解策略 |
|------|--------|------------|
| [风险] | [高/中/低] | [策略] |

## 待解决问题
- [需要人工输入的问题]
```

## 并行化机会

当有多个 agent 或会话可用时：

- **可安全并行：** 独立功能切片、已实现功能的测试、文档
- **必须串行：** 数据库迁移、共享状态变更、依赖链
- **需要协调：** 共享 API 契约的功能（先定义契约，再并行）

## 常见的合理化借口

| 合理化借口 | 现实 |
|---|---|
| "我会边做边想" | 这就是你怎么最终得到一团混乱和返工的。10 分钟规划省下数小时。 |
| "任务显而易见" | 写下来无论如何。显式任务暴露隐藏依赖和被遗忘的边界情况。 |
| "规划是开销" | 规划就是任务。没有规划的实现只是打字。 |
| "我可以全装在脑子里" | 上下文窗口有限。书面计划跨会话边界和压缩后存活。 |

## 危险信号

- 没有书面任务列表就开始实现
- 任务说"实现功能"没有验收标准
- 计划中没有验证步骤
- 所有任务都是 XL 大小
- 任务间没有检查点
- 没有考虑依赖顺序

## 验证

开始实现前，确认：

- [ ] 每个任务有验收标准
- [ ] 每个任务有验证步骤
- [ ] 任务依赖已识别并正确排序
- [ ] 没有任务涉及超过约 5 个文件
- [ ] 主要阶段间存在检查点
- [ ] 人类已审查并批准计划

## 参见

验收标准是每个任务的，回答"我们构建了正确的东西吗？"。它们叠加在项目级的完成定义之上，完成定义是每个任务必须通过的门槛。见 `../../references/definition-of-done.md`。
