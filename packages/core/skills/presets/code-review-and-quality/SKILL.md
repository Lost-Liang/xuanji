# 代码审查与质量

## 概述

带质量门的多维度代码审查。每个变更在合并前都要审查——无例外。审查覆盖五个维度：正确性、可读性、架构、安全性和性能。

**批准标准：** 当变更确实改善整体代码健康状况时批准，即使它并不完美。完美代码不存在——目标是持续改进。不要因为变更不是你会采用的写法就阻塞它。如果它改善了代码库并遵循项目约定，就批准它。

## 何时使用

- 合并任何 PR 或变更之前
- 完成功能实现后
- 当另一个 agent 或模型生成了需要评估的代码
- 重构现有代码时
- 任何 bug 修复后（同时审查修复和回归测试）

## 五维度审查

每次审查从以下维度评估代码：

### 1. 正确性

代码是否做了它声称要做的事？

- 是否匹配规格或任务需求？
- 边界情况是否处理（null、空值、边界值）？
- 错误路径是否处理（不只是正常路径）？
- 是否通过所有测试？测试是否确实测试了正确的事情？
- 是否有差一错误、竞态条件或状态不一致？

### 2. 可读性与简洁性

另一个工程师（或 agent）能否在没有作者解释的情况下理解这段代码？

- 名称是否具有描述性并与项目约定一致？（没有上下文时不要用 `temp`、`data`、`result`）
- 控制流是否直观（避免嵌套三元表达式、深层回调）？
- 代码组织是否合理（相关代码分组、模块边界清晰）？
- 是否有应该简化的"巧妙"技巧？
- **能否用更少的行数完成？**（1000 行能完成的事用 100 行是失败）
- **抽象是否值得其复杂度？**（在第三个用例出现前不要泛化）
- 注释是否有助于澄清不明显的意图？（但不要注释明显的代码）
- 是否有死代码残留：空操作变量（`_unused`）、向后兼容垫片或 `// removed` 注释？
- **新的条件分支是否附加到无关流程上？** 这是设计异味，不是小问题——把逻辑推到独立的 helper、状态或策略中，而不是纠缠现有路径。
- **同一形状上是否有重复的条件判断？** 它们信号着缺失的模型或调度器。"临时"分支通常是永久债务。

### 3. 架构

变更是否适合系统的设计？

- 是否遵循现有模式或引入新模式？如果是新的，是否有理由？
- 是否保持清晰的模块边界？
- 是否存在应该共享的代码重复？
- 依赖是否流向正确方向（无循环依赖）？
- 抽象层次是否适当（不过度工程，也不过度耦合）？
- **这次重构是减少了复杂度还是只是转移了它？** 计算读者跟随变更需要持有的概念数量。如果"更简洁"的版本让这个数量不变，那就不叫更简洁——优先选择能让整个分支、模式或层消失的重构，而不是重新集中相同逻辑的重构。优先删除抽象而不是修饰它。
- **功能特定的逻辑是否泄漏到共享或通用模块中？** 将逻辑保留在其所属层，复用现有的权威 helper 而不是近似副本，不要让架构漂移正常化。
- **类型边界是否明确？** 质疑无理由的 `any`/`unknown`/可选/类型转换和静默回退——它们掩盖了不清晰的不变量。让边界明确通常会让周围的控制流更简单。

### 4. 安全性

详细安全指南见 `security-and-hardening`。变更是否引入漏洞？

- 用户输入是否验证和净化？
- 密钥是否远离代码、日志和版本控制？
- 需要认证/授权的地方是否检查？
- SQL 查询是否参数化（无字符串拼接）？
- 输出是否编码以防止 XSS？
- 依赖是否来自可信来源且无已知漏洞？
- 外部来源的数据（API、日志、用户内容、配置文件）是否被视为不可信？
- 外部数据流是否在系统边界验证后才用于逻辑或渲染？

### 5. 性能

详细分析和优化见 `performance-optimization`。变更是否引入性能问题？

- 是否有 N+1 查询模式？
- 是否有无限循环或不受约束的数据获取？
- 是否有应该异步的同步操作？
- UI 组件中是否有不必要的重渲染？
- 列表端点是否缺少分页？
- 热路径中是否创建大对象？

## 结构性修复

当你标记结构性问题时，提出修复方案——不只是指出问题。只说"这很复杂"的审查让作者猜测。采用命名的重构方式：

- **用类型模型或显式调度器替换条件链。**
- **将重复分支合并为更清晰的单一流程。**
- **分离编排和业务逻辑**，让各自独立可读。
- **将功能特定逻辑从共享模块移出** 到拥有该概念的包中。
- **复用权威 helper** 而不是临时的近似副本。
- **让类型边界明确**，使下游分支消失。
- **删除只增加间接层而不澄清 API 的透传包装器。**
- **提取 helper，或将大文件拆分** 为专注的模块。

优先选择能减少活动部件的修复方案，而不是分散相同复杂度的方案。

## 变更大小

小而专注的变更更容易审查、更快合并、更安全部署。目标这些大小：

```
约 100 行变更   → 好。可一次审查完成。
约 300 行变更   → 可接受，如果是单一逻辑变更。
约 1000 行变更  → 太大。拆分它。
```

**关注文件大小，不只是 diff 大小。** 小 diff 仍可能把文件推过健康边界——单个文件约 1000 *总*行（不同于上面约 1000 *变更*行的阈值）是常见的检查信号，不是硬性上限。当变更显著增加了已经很大的文件时，问是否应该先提取 helper、子组件或模块，然后再堆叠更多。先分解，再添加。

**什么算"一个变更"：** 单个自包含的修改，解决一件事，包含相关测试，提交后系统仍能运行。功能的一部分——不是整个功能。

**变更过大时的拆分策略：**

| 策略 | 方法 | 适用场景 |
|----------|-----|------|
| **堆叠** | 提交小变更，基于它开始下一个 | 顺序依赖 |
| **按文件组** | 分离需要不同审查者的组的变更 | 横切关注点 |
| **水平** | 先创建共享代码/存根，再创建消费者 | 分层架构 |
| **垂直** | 拆分为功能的全栈小切片 | 功能开发 |

**何时大变更可接受：** 完整文件删除和自动化重构，审查者只需验证意图，不需验证每一行。

**将重构与功能开发分开。** 重构现有代码并添加新行为的变更是两个变更——分别提交。小清理（变量重命名）可由审查者决定是否包含。

## 变更描述

每个变更都需要能在版本控制历史中独立存在的描述。

**第一行：** 简短、祈使语气、独立。"删除 FizzBuzz RPC"而不是"正在删除 FizzBuzz RPC"。必须足够有信息量，让搜索历史的人无需阅读 diff 就能理解变更。

**正文：** 变更了什么以及为什么。包含代码本身看不到的上下文、决策和推理。在相关处链接到 bug 编号、基准测试结果或设计文档。存在缺陷时承认方案缺点。

**反模式：** "修复 bug"、"修复构建"、"添加补丁"、"将代码从 A 移到 B"、"第一阶段"、"添加便利函数"。

## 审查流程

### 步骤 1：理解上下文

在看代码之前，理解意图：

```
- 这个变更试图完成什么？
- 它实现的是哪个规格或任务？
- 预期的行为变更是什么？
```

### 步骤 2：先审查测试

测试揭示意图和覆盖：

```
- 变更有测试吗？
- 它们测试的是行为（不是实现细节）吗？
- 边界情况是否覆盖？
- 测试名称是否有描述性？
- 如果代码改变，测试能捕获回归吗？
```

### 步骤 3：审查实现

带着五个维度遍历代码：

```
对于每个变更的文件：
1. 正确性：这段代码是否做了测试说它应该做的事？
2. 可读性：我能否在没有帮助的情况下理解它？
3. 架构：它适合系统吗？
4. 安全性：有漏洞吗？
5. 性能：有瓶颈吗？
```

### 步骤 4：分类发现

用严重程度标记每条评论，让作者知道什么是必须的什么是可选的：

| 前缀 | 含义 | 作者行动 |
|--------|---------|---------------|
| （无前缀） | 必须修改 | 合并前必须处理 |
| **严重：** | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **小问题：** | 次要、可选 | 作者可忽略 —— 格式、风格偏好 |
| **可选：** / **建议：** | 建议 | 值得考虑但不必须 |
| **供参考** | 仅供参考 | 无需行动 —— 为将来参考提供上下文 |

这防止作者将所有反馈视为强制性，浪费时间在可选建议上。

**优先呈现重要内容。** 按影响力排序发现：正确性和安全优先，然后是结构性退化和错失的简化机会，然后是其他。不要把真正问题埋在装饰性小问题下——几个高确信评论胜过一长串。如果你有一个结构性问题和十个小问题，结构性问题*就是*审查。

### 步骤 5：验证验证故事

检查作者的验证说明：

```
- 运行了什么测试？
- 构建是否通过？
- 是否手动测试了变更？
- UI 变更有截图吗？
- 有前后对比吗？
```

## 多模型审查模式

用不同模型获得不同审查视角：

```
模型 A 编写代码
    │
    ▼
模型 B 审查正确性和架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人类做最终决定
```

这能捕获单个模型可能错过的问题——不同模型有不同的盲点。

**审查 agent 的示例提示：**

```
审查此代码变更的正确性、安全性和是否符合项目约定。
规格说明 [X]。变更应该 [Y]。
将问题标记为严重、必须、可选或小问题。
```

## 死代码清理

任何重构或实现变更后，检查孤立代码：

1. 识别现在不可达或未使用的代码
2. 明确列出
3. **删除前先询问：** "我应该删除这些现在未使用的元素：[列表] 吗？"

不要让死代码堆积——它会困扰未来的读者和 agent。但不要静默删除你不确定的东西。有疑问时，问。

```
发现的死代码：
- src/utils/date.ts 中的 formatLegacyDate() —— 已被 formatDate() 替代
- src/components/ 中的 OldTaskCard 组件 —— 已被 TaskCard 替代
- src/config.ts 中的 LEGACY_API_URL 常量 —— 无剩余引用
→ 安全删除这些吗？
```

## 审查速度

慢审查阻塞整个团队。上下文切换审查的成本低于施加给其他人的等待成本。

- **在一个工作日内响应** —— 这是上限，不是目标
- **理想节奏：** 审查请求到达后不久响应，除非处于深度编码中。典型变更应在一天内完成多轮审查
- **优先快速单独响应** 而非快速最终批准。即使需要多轮，快速反馈也能减少挫败感
- **大变更：** 要求作者拆分它们，而不是审查一个巨大的变更集

## 处理分歧

解决审查争议时，应用此层级：

1. **技术事实和数据** 优于意见和偏好
2. **风格指南** 是风格问题的绝对权威
3. **软件设计** 必须基于工程原则评估，不是个人偏好
4. **代码库一致性** 可接受，如果不会降低整体健康度

**不要接受"我以后会清理"。** 经验表明延期清理很少发生。要求提交前清理，除非是真正的紧急情况。如果周围问题无法在本次变更中解决，要求提交 bug 并自行分配。

## 审查中的诚实

审查代码时——无论由你、另一个 agent 还是人类编写：

- **不要走过场。** 没有审查证据的"看起来没问题"对谁都没帮助。
- **不要软化真正的问题。** 当这是一个会上生产的 bug 时说"这可能是个小问题"是不诚实的。
- **尽可能量化问题。** "这个 N+1 查询会给列表中每个项目增加约 50ms"比"这可能很慢"更好。
- **对有明显问题的方案提出异议。** 审查中的阿谀奉承是失败模式。如果实现有问题，直接说并提出替代方案。
- **优雅接受否决。** 如果作者有完整上下文并不同意，尊重他们的判断。评论代码，不是人——将个人批评重构为关注代码本身。

## 依赖纪律

代码审查的一部分是依赖审查：

**添加任何依赖之前：**

1. 现有技术栈能解决吗？（通常能。）
2. 依赖多大？（检查包体积影响。）
3. 是否积极维护？（检查最后提交、开放问题。）
4. 是否有已知漏洞？（`npm audit`）
5. 许可证是什么？（必须与项目兼容。）

**规则：** 优先使用标准库和现有工具，而非新依赖。每个依赖都是负债。

**升级现有依赖** 是代码变更，最危险的升级是那些批量合并并带有"升级依赖"消息的升级。用同样的纪律审查它们：

1. **阅读变更日志，不只是版本号。** 语义版本是维护者可能未遵守的承诺——"补丁"可能带有行为变更。对于主版本升级，阅读迁移说明并找出破坏性变更。
2. **每次变更一个依赖。** 单独升级并合并（或小相关组）。当批量升级破坏构建时，你不知道是哪个包造成的；单包变更让原因明显且回滚干净。
3. **让测试决定。** 升级由前后绿套件验证，不是"安装成功了"。如果依赖行为的覆盖不足，那个缺口才是真正发现的问题——先添加测试。
4. **关注传递图。** 大多数安装的包是没人直接选择的。审查锁文件 diff，不只是 `package.json`；单次直接升级可能拉入数十个间接变更。
5. **保持锁文件诚实。** 提交它，审查它的 diff，永远不要手工编辑。锁文件是真正固定发布内容的文件。

关于分类 `npm audit` 发现和供应链风险（抢注、受损维护者），遵循 `security-and-hardening` skill——本节覆盖升级*工作流*，那个覆盖安全裁决。

```markdown
### 架构
- [ ] 遵循现有模式
- [ ] 无不必要的耦合或依赖
- [ ] 抽象层次适当
- [ ] 重构减少复杂度而非转移它
- [ ] 共享模块中无功能逻辑；文件保持在健康大小内

### 安全性
- [ ] 代码中无密钥
- [ ] 边界验证输入

- [ ] 无 N+1 模式

- [ ] 列表端点有分页

### 验证
- [ ] 测试通过
- [ ] 构建成功
- [ ] 手动验证完成（如适用）

### 结论
- [ ] **批准** —— 准备合并
- [ ] **要求修改** —— 问题必须处理
```

## 常见的合理化借口

| 合理化借口 | 现实 |
|---|---|
| "它能工作，这就够了" | 能工作但不可读、不安全或架构错误的代码会产生复利债务。 |
| "我写的，所以我知道它是正确的" | 作者对自己的假设视而不见。每个变更都受益于另一双眼睛。 |
| "我们以后会清理" | 以后永远不会来。审查是质量门——使用它。要求合并前清理，不是之后。 |
| "AI 生成的代码可能没问题" | AI 代码需要更多审查，不是更少。它自信且看似合理，即使错误。 |
| "测试通过了，所以没问题" | 测试是必要但不充分的。它们不捕获架构问题、安全问题或可读性问题。 |
| "重构让它更简洁" | 转移复杂度不是减少它。如果读者仍然持有相同数量的概念，结构没有改善——寻找让分支消失的版本。 |
| "只是给这个文件的小添加" | 小 diff 仍可能把文件推过健康大小并将分支附加到无关流程。评判结果结构，不是 diff 大小。 |
| "只是版本升级" | 升级是你没编写的行为变更。阅读变更日志；语义版本不保证不破坏。 |
| "我会用一个 PR 升级所有东西以节省时间" | 破坏构建的批量升级隐藏了是哪个包造成的。每次变更一个依赖让原因和回滚都干净。 |

## 危险信号

- PR 没有任何审查就合并
- 审查只检查测试是否通过（忽略其他维度）
- 没有实际审查证据的"看起来没问题"
- 安全敏感变更没有安全重点审查
- "太大无法正确审查"的大 PR（拆分它们）
- Bug 修复 PR 没有回归测试
- 审查评论没有严重程度标签 —— 让人不清楚什么是必须的什么是可选的
- 接受"我以后会修" —— 这永远不会发生
- 重构移动代码但没有减少读者需要持有的概念数量
- 变更增加已经很大的文件而不是分解它
- 新条件分散到无关代码路径中（缺失抽象）
- 近似复制现有权威 helper 的临时 helper，或放在共享模块中的功能逻辑
- 批量"升级依赖" PR 没有变更日志审查且没有按包隔离
- 手工编辑、未提交或合并时未审查 diff 的锁文件变更
